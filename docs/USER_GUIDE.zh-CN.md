# 开发智能中枢使用手册

这份手册面向每天使用网页的项目负责人。首次安装与故障恢复的细节另见 [README](../README.md) 和 [运维手册](OPERATIONS.md)。项目目前是开发中的 `0.1.0`；页面展示的是本机已激活配置和最近一次成功读取的数据，具体功能取决于你的账号、岗位权限和数据源状态。

## 先从这四步开始

1. 在项目目录执行 `./scripts/Manage-MyDashboard.ps1 -Action Status`，确认服务健康。未启动时执行 `./scripts/Manage-MyDashboard.ps1 -Action Start -OpenBrowser`。网页地址是 `http://127.0.0.1:4173`。
2. 打开**总览**，先看顶部的更新时间、数据源提示和“现在轮到我 / 等待别人 / 需要你确认”。有读取错误时，先到**系统状态**查原因；旧数据仍可能留在页面上。
3. 打开**数字员工**，看各岗位的“当前任务”和最近行动。需要人工决定的事项在**确认中心**处理；任务结果在**工作台账**查看。
4. 结束前看**工作台账**中的“阻塞”和“等待”，再看**系统状态**。不要把“已派发给岗位”理解成“GitHub 已修改”或“任务已完成”。

首次安装使用仓库示例配置时，GitHub、钉钉、代码执行和主动岗位默认关闭。需要先完成本机配置并激活，页面才会出现真实业务数据。

## 看懂首页和各页面

| 页面 | 主要用途 | 你通常要做的事 |
| --- | --- | --- |
| 总览 | 汇总今天的行动信号、PR 员工作业和最近一次定时汇报 | 先看是否轮到自己、是否有确认请求或数据源错误 |
| Pull Requests | 按“现在轮到我、等待别人、需要确认、历史待清理”查看 PR | 点开 PR 看依据，再到 GitHub 核对当前状态 |
| Issues | 查看当前 GitHub 账号分配给自己的开放 Issue | 决定自己处理、在 GitHub 转交，或创建共享工作 |
| 版本 | 看里程碑和 Release | 了解版本进度 |
| 钉钉信号 | 看钉钉消息、待办和定时工作汇报 | 根据来源决定是否跟进；钉钉认证错误需先恢复登录 |
| 数字员工 | 看岗位、使用的大脑、权限、最近行动和当前任务 | 按岗位“立即运行”或“暂停岗位”；处理统一确认队列 |
| 记忆搜索 | 查员工保留的历史结论和引用 | 回溯一项决策的依据 |
| 工作流 | 查看路由规则和分派记录，模拟路由，创建共享工作 | 核对任务去了哪个岗位，必要时人工提出明确目标 |
| 工作台账 | 看持久任务、状态、尝试次数、审计时间线和本地代码任务 | 判断是否真正完成、等待什么、为什么阻塞 |
| 自动化测试库 | 查看和管理受控测试脚本 | 核对代码任务可运行的固定测试 |
| 配置中心 | 管理账号、岗位、模型、权限、路由和工作区等配置 | 保存草稿、预览影响、请求激活确认、按提示重启 |
| 系统状态 | 看服务就绪、恢复阻塞、备份 | 排查故障，创建备份 |

页面顶部的**刷新**会请求新数据。它不会重启服务、修复登录、重新执行失败任务，也不会改变 GitHub 上的 PR。页面上的“更新于”指本地快照时间；遇到来源错误，应以对应 GitHub 或钉钉页面的当前事实核对。

### Issue 后面的 PR 状态

每条开放 Issue 下方会显示“PR 关联”和“关闭判断”。点开 Issue 可查看 PR 链接、状态，以及它是 GitHub **正式关联**，还是只在讨论中**提及**了这个 Issue。

| 显示 | 怎么理解 |
| --- | --- |
| 未发现关联 PR | 当前读取范围内没有正式关联或提及；仍可能有未关联的修复工作 |
| 有 PR 提及，待核对 | PR 引用了 Issue，但不能据此认定它负责完全解决 |
| 关联 PR 进行中 | 正式关联的 PR 还未合并，先跟进代码和验证 |
| 关联 PR 已关闭 | PR 关闭但未合并，核对是否需要另一份修复 |
| 关联 PR 已合并，待验收 | 代码已合并；检查问题复现、测试结果和验收范围后再决定是否关闭 Issue |
| PR 关联待刷新 / 未查全 | 数据缺失或 GitHub 记录超过读取范围，到 GitHub 核对 |

**PR 合并不等于 Issue 已解决。** 页面只给出下一步提示，不自动判定“完全解决”，也不会自动关闭 Issue。GitHub 的正式关闭关联在 PR 合入目标默认分支时可能自动关闭 Issue；跨仓库引用或只写编号通常不能替代正式关联。关闭前请以实际验收和 Issue 目标为准。

## 一项工作怎样推进

### 先用好自动 Review

在配置中心启用自动 Review 后，PR 工程师独立巡查；开发任务或主控等待子任务，不会占住它的执行队列。数据刷新仍需成功，发布前仍会核对当前 Head、分配状态和授权。自动 Review 的发布结果、失败诊断及后续交接，在**数字员工 → 确认历史 → 自动 Review 记录**查看。

岗位的“已启用”只表示没有暂停。是否正在推进，要看最近行动、运行结果和工作台账；不能根据这个标记认定任务完成。

会话保存或恢复、CLI 清理或进程结束故障，集中出现在**数字员工 → 系统故障 · 待维护**，不再逐任务自动弹窗。展开同类故障可查看受影响任务。维护人员确认修复后，可逐项打开原请求重试；查看列表不会答复、删除或重试任务。需求取舍、缺少配置和外部动作授权仍按原规则处理。

### 安排你的工作

先根据截止时间、影响范围和阻塞关系挑出当天必须处理的工作，再分配给具体负责人。系统现有排序主要参考明确优先级、评审分配时间和任务依赖，不能代替你的业务判断。开发闭环优先用于需求清楚、能本地构建和测试的小任务；需要实机或业务验收的部分，写进验收条件并交给对应人员。

常见路径是：**外部事件或人工请求 → 路由到岗位 → 员工判断 → 等待条件或请求确认 → 受控执行 → 结果回到台账**。

例如想处理一条 PR：

1. 在 **Pull Requests** 打开该 PR，核对仓库、编号、Head 和当前 CI。需要自己明确发起的工作，可在**工作流 → 创建共享工作**选择“PR 推进”，填写仓库、PR 编号、目标和验收条件，再点“创建并交给中枢”。
2. 在**数字员工 → 查看该岗位任务**或**工作台账**找对应工作项。路由到 `pr-engineer` 只表示岗位收到任务，不表示 Review 已发布。
3. 未开启相应自动模式时，有请示或外部动作需到**确认中心**核对完整目标、账号、Head、正文与依据后确认。自动 Review 和“自动修复我的 PR”各自在已授权范围内连续处理，结果留在台账和历史中。
4. 回到**工作台账**看最终状态；GitHub 写入后再打开 GitHub PR 核对实际结果。如果 PR 换了 Head、关闭或合并，旧作业会保留为历史记录，不应按旧判断继续操作。

人工“创建共享工作”只能填写业务目标；岗位、工具和权限由可信路由与配置决定。系统不会因为你创建了一项工作就自动获得代码写入或 GitHub 写入权。

## 三种容易混淆的队列

| 名称 | 含义 | 当前可用操作 |
| --- | --- | --- |
| GitHub 分配给我的 Issue/PR | GitHub 上的人员责任关系 | 在 GitHub 调整 Assignee；本机页面主要用于查看和判断 |
| AI 岗位任务 | 工作台账中交给 `developer`、`tester` 等岗位的任务 | 可暂停或恢复整个岗位；普通任务目前没有通用的逐项暂停、删除或转交人员按钮 |
| 确认队列 | 等待你答复、批准或驳回的具体请求 | 逐项核对后答复、确认、驳回或“稍后再看” |

**稍后再看**只让当前弹窗暂时不再弹出，原请求仍留在队列。**驳回请示**会把原工作项转入阻塞。**提交答复**把答复写进台账，让原岗位继续处理。普通外部动作仍可能分别确认 Review、代码任务、应用变更包、push 或 merge。开启自动模式后，符合范围的 Review 发布或我的 PR 修复流程免逐项确认；开关不适用的动作仍沿用原授权方式。

原任务已取消、完成或被新任务替代后，对应的旧内部请示会在启动或台账协调周期中自动归档。原问题、来源和归档原因仍保留，系统不会替你作答或重试任务。“稍后再看”不会触发归档，也不会创建新的任务；它只在当前浏览器会话中隐藏该项。

遇到 **“系统会话保存或恢复故障”**，需要维护人员修复本地会话存储与恢复流程。这类故障不要求你补充业务判断或模型配置。**“修复后重试”**只把原任务重新排队，不会自动修复会话；修复前可选“稍后再看”，保留原会话历史。

目前只有 Review 发布后的特定测试交接能按配置中的候选人转交 GitHub Assignee；它不等于“把所有分配给我的 Issue/PR 自动分给团队成员”。要转交真实人员，先核对职责和 GitHub 账号，不要把 AI 岗位任务数当作人员待办数。

## 状态和“尝试次数”

| 状态 | 解释 | 建议动作 |
| --- | --- | --- |
| 待领取 / 处理中 | 岗位尚未开始 / 正在处理 | 看岗位是否暂停、模型是否可用和最近行动 |
| 等待答复 / 等待条件 / 等待授权 | 在等你、CI 等外部事实，或某项权限/外部结果 | 按具体原因处理；等待不等于失败 |
| 等待重试 | 已安排下一次自动尝试 | 先看失败原因，避免无效重试 |
| 已阻塞 | 当前工作项停止自动推进 | 看“台账原因”和审计时间线，再修复具体条件 |
| 已完成 / 已取消 / 已替代 | 工作项已经结算、取消或被新来源状态取代 | 到来源页面核对最终事实；旧记录留在历史中 |

“**尝试 N 次**”是岗位领取并处理该工作项的次数，不是模型调用次数，也不是 GitHub 写入次数。一次尝试可能完成交接、等待条件、在权限门禁前失败，或因租约超时结束。`intent_failed` 表示某个意图派发失败；`decision_attempts_exhausted` 表示决策尝试达到上限。**阻塞不一定是你按了驳回**：权限策略、来源读取失败、失效的 Head 和重试上限也会自动阻塞。其他独立任务通常继续运行，依赖该结果的下游任务才会等待。

工作台账只对符合条件的 `decision_attempts_exhausted` PR 根任务提供“重新排队一次”。先解决原错误再点它；普通台账任务没有通用的逐项重试按钮。**本地代码任务**的“安全暂停 / 恢复执行 / 取消任务”只控制该代码任务，不控制整个 AI 岗位队列。

## 确认 Review 和代码动作

### 自动 Review

在**配置中心 → GitHub 动作**可以开关“自动 Review”和“自动分配 Review 后续”。新配置默认勾选；旧配置保留原来的逐项确认方式，需明确开启后生效。设置保存、预览并激活后，按提示受管重启。

- 范围：最近 **24 小时**内，别人通过 GitHub **Assignee** 分配给你的、仍打开且非 Draft 的 PR。按实际 Assign 事件时间计算；Request review、更新 PR 或推送新提交都不会刷新这个时间或单独启动自动评审。自己的 PR 不自动发布 Review。
- 执行：PR 工程师读取当前代码和讨论，生成有证据的 Review，通过持久队列自动发布，免逐项确认。同一 Head 已有你的明确评审结论时跳过；Head、账号、授权或当前分配变化时停止过期动作。结果未知时禁止盲目重放。
- 模型与内容：实际模型在 **配置中心 → 数字员工 → PR 工程师** 中配置。评审使用当前 Head 绑定的代码差异、PR 说明、讨论、已有 Review 和检查结果；不会自动运行构建或测试。Codex CLI 评审会取得完整变更清单和当前提交的最终差异，落盘为 `review-manifest.json`、`review.diff`，并通过专用只读工具分段读取；还可查阅当前提交和基线提交的相关源码。提示词内的截断材料只是预览，不构成整个评审的读取上限。读取未完成时不会把部分意见作为完整 Review 发布。其他不支持读取工具的模型仍只能分析已提供的材料。
- 评审流程：后台自动加载项目内的 [quick-pr-review 技能](../src/skills/quick-pr-review/SKILL.md)，依次检查改动目标、代码行为、验证证据和未覆盖范围，再生成结论。它是基于所提供材料的单模型评审流程，可以配合 `high` 推理强度使用；复杂改动或材料不足时会指出需要深入检查的部分。
- 评论格式：先给“通过 / 需要修改 / 暂无法判断”的结论，再按需列“问题、已检查、下一步”。问题应包含位置、触发条件、影响与修复建议；已有手工测试需按其实际覆盖范围考虑。短 Head 和代码链接放在折叠的“评审范围”中，内部审计字段留在系统记录里。
- 交接：成功发布后，`APPROVE` 交给对应 Qt / B/S 配置中的首位可用测试人员；`REQUEST_CHANGES` 和 `COMMENT` 交回 PR 作者。三种结果都先添加下一责任人，再移除你自己的 Assignee；保留其他已有负责人。`COMMENT` 不代表通过或不通过，交回作者处理评论或补充材料。产品或测试名单无法确定时保留人工确认；发布失败、结果未知或交接未完成时，不应视为本轮已交接。
- 再次评审：作者修改后重新 Assign 给你，系统按新的 Assign 时间识别下一轮，评审新的 Head。仅推送代码而未重新 Assign 给你，不会因残留的 Request review 启动新一轮；即使移除 Assignee 暂未完成，已发布 Review 的旧 Assign 也不会继续触发新提交的评审。同一 Head 已有你的通过或要求修改结论时仍跳过，避免重复评审。
- 查看：**数字员工 → 确认中心 → 只读确认历史 → 记录：自动 Review 记录**。这里显示 PR、通过/需修改/评论、Head、时间、GitHub 链接、发布结果与交接结果。“发布完成”不代表测试通过或可以合并；交接失败会单独显示，不会重新发布 Review。
- 关闭自动分配后仍可自动发布 Review；关闭自动 Review 后，新发布需逐项确认。旧任务、手动指派的任务和审计记录不会被删除。上述开关不授权自动合并、推送代码或关闭 Issue。

### 自动修复我的 PR

在**配置中心 → GitHub 动作**开启“**自动修复我的 PR**”，保存、预览并激活配置，再按提示受管重启。这个开关与“自动 Review”独立：前者修复你自己写的 PR，后者评审别人 Assign 给你的 PR。新配置和没有该字段的旧配置默认关闭；明确开启后生效。

- 自己仍打开的 PR 收到他人的评审修改意见后，系统交给**开发工程师**读取意见和当前代码，判断需要修改的内容。
- 开发决策和代码任务都会读取当前 Head 对应的完整待处理评审意见及相关回复；页面摘要不构成读取上限。内容过大或读取失败会明确报错，不会静默丢掉部分意见后继续推送。
- 在隔离工作区中修改、运行配置的验证并更新**原 PR 分支**，无需分别确认代码任务和本轮 push。你的本地工作文件、分支和暂存区保持原样；无需另行开放通用 `push` 权限。
- 系统自动获取当前 Head 所需的 Git 对象。启用前需要配好受控 Git 镜像与验证任务；仅配置“仓库预检”时，结果只代表预检通过，不代表完整编译或产品测试通过。
- 开关免除重复批准，不会跳过验证。来源或 Head 已变化、验证失败、缺少工作区或无法判断如何修改时，记录具体原因并等待处理，不强行推送。
- 到**数字员工 → 开发工程师 → 查看该岗位任务**、**工作台账**和对应**本地代码任务**查看进度与验证结果；**确认中心 → 只读确认历史**会标记“自动修复我的 PR”的开发任务和推送结果。同一轮已推送的意见等待复审；新提交不代表他人已认可，也不会自动合并 PR。
- 关闭后，后续修复恢复普通确认流程；已经产生的任务、验证产物和审计记录仍保留。

Review 建议是系统判断，可能遗漏作者已完成的手工测试或新提交。人工确认前至少核对 PR 的当前 Head、CI、作者提供的验证记录、建议正文和目标账号。成功发布 Review 后，系统可能按配置创建下一棒测试或跟进任务。选择测试负责人并完成受控交接后，GitHub Assignee 才会转交；选择外部 Reviewer 目前只创建本地跟进任务，不直接发送 GitHub 的 Request review。

普通模式下，批准创建**本地代码任务**只建立隔离执行任务，变更包应用和 GitHub 写入各有独立确认。“自动修复我的 PR”直接从隔离任务生成受控提交并推送原 PR，不需要先把变更包应用到你的本地工作区。若结果标为 `unknown` 或页面要求对账，不要反复点击同一外部动作；先在**系统状态**和 GitHub 核对。

## 配置、暂停和备份

- **暂停岗位**会阻止该岗位领取新工作，队列和审计记录仍保留；“恢复岗位”后再继续。仅想停止一个任务时，不要把岗位整体暂停误当成单项取消。
- 在**配置中心**修改设置时，先保存本地草稿，点“预览影响”，再“请求激活确认”。确认激活或回滚后，按页面提示使用受管 `Restart`；未重启前，以页面显示的实际运行版本为准。
- 配置、账号和数据保存在本机。升级或较大调整前，可在**系统状态 → 创建备份**保存可验证备份。不要手工改写 `data/` 台账文件以清除队列。
- 密钥放在服务环境变量中，不写入配置文件或公开仓库。不同岗位可使用不同模型；模型配置不会增加岗位权限。

## 钉钉汇报与常见故障

**邮件摘要**：在配置中心的钉钉设置中打开“邮件自动摘要（最近 24 小时）”，激活后重启生效。系统只读采集当前唯一的企业邮箱收件箱，使用现有本地摘要模型汇总，优先展示明确 @你、分配给你、需要回复或决策的邮件。同一主题合并，已出现在 PR/Issue 列表的常规 GitHub 通知不重复展示，具体讨论意见仍保留。摘要与依据在“钉钉信号”查看，并加入 09:00、12:00、15:00、18:00、20:00 的定时汇报。关闭开关后停止采集；不会回复、标记已读或删除邮件。邮件授权失败时保留上次摘要，正文不完整会明确提示，附件内容需到邮箱核对。

配置好钉钉后，定时汇报按上海时间在 **09:00、12:00、15:00、18:00、20:00** 运行：09:00 是每日总览，12:00/15:00/18:00 是进展，20:00 是收口。最新汇报在**钉钉信号**查看。若钉钉显示认证过期，先按提示对原 profile 重新授权，再刷新；页面刷新不能替你恢复登录态。

| 看到的情况 | 先检查什么 |
| --- | --- |
| “读取确认队列失败（503）” | **系统状态**的就绪与数据源错误；主页面可以继续显示旧快照，确认队列会重试 |
| “Failed to fetch” | 服务是否仍在运行、浏览器是否能访问 `127.0.0.1:4173`；再看受管 `Status` |
| 钉钉消息查询被限流 | 该来源本轮未更新，旧记录仍保留；等待下一次定时刷新。持续出现时联系钉钉服务端排查 |
| “Provider 不可用” | 对应岗位的模型、CLI 安装和同一服务账号的登录状态；不要仅靠重排任务来解决 |
| `policy-denied` | 岗位权限、仓库到受信工作区映射、允许的操作；请求可能在执行前被拦下 |
| PR 已合并但旧作业还可见 | 先在 GitHub 核对；数字员工中的“历史作业”保留旧 Head 判断，不表示当前仍需处理 |
| 阻塞任务很多 | 在**工作台账**逐条看原因和来源；不要一次性重试或删除全部记录 |

需要更深的启动、备份、恢复和凭据排查步骤，参见 [运维手册](OPERATIONS.md)。

# PR 更新时间窗口设计

**日期：** 2026-08-12

**状态：** 已批准（2026-08-12，负责人批准推荐设计）

**适用范围：** MyDashboard 自动发现的、与当前 GitHub 账号相关的开放 PR

## 1. 背景

MyDashboard 当前通过 GitHub CLI 分别搜索“指派给我”和“由我创建”的全部开放 PR，合并后再逐个读取详情。这个入口没有时间边界，因此多年未更新的 PR 也会进入快照、岗位路由和确认流程。`prResponsibility.historicalAfterDays` 只负责展示与责任分类，不能阻止旧 PR 被发现、抓取详情或产生工作。

本设计在 GitHub PR 源头增加可配置的 `updatedAt` 时间窗口。窗口首先减少详情抓取，再通过可信的生命周期事件撤销已离开自动发现范围的工作授权。它不能绕过现有逐项确认，也不能把一次源读取失败误判成 PR 已离开范围。

## 2. 目标

1. 页面支持“最近 N 天”和“固定日期范围（YYYYMMDD–YYYYMMDD）”。
2. 新配置推荐最近 7 天；旧配置未声明窗口时保持原有不限时间行为。
3. 窗口以 GitHub 返回的 PR `updatedAt` 为唯一判断字段。
4. 在读取 PR 详情前完成严格本地过滤，避免为范围外 PR 执行 `gh pr view`。
5. 一次刷新只使用一个冻结后的有效窗口；assigned 与 authored 查询必须共用它。
6. 健康刷新中离开范围的 PR 只产生一次可信 `left_scope` 生命周期变化，并撤销相关自动执行授权。
7. GitHub 源失败、结果不完整或 `updatedAt` 异常时失败关闭：保留上一份 PR 快照，不产生 `left_scope`。
8. 同一 Head 的 PR 以后重新进入范围时创建新的授权纪元；旧提案和旧确认不能复活。

## 3. 非目标

- 不改变 `prResponsibility.historicalAfterDays` 的展示和责任分类含义。
- 不允许岗位大脑自行扩大时间窗口，也不接受模型输出的日期边界。
- 不把日期窗口编码进 `sourceScopeId`；源身份与过滤策略保持分离。
- 不取消真实 GitHub Review、评论、更新分支、push 或 merge 的逐项确认。
- 不把“自动发现范围”当成负责人显式指定 PR 的唯一授权来源。
- 不在本功能中改变 Issue、版本、钉钉或其他数据源的时间范围。

## 4. 配置契约

`githubRead` 增加可选字段 `pullRequestUpdatedWindow`。字段完全省略表示兼容旧行为：不按更新时间过滤。

### 4.1 最近 N 天

```json
{
  "githubRead": {
    "enabled": true,
    "pullRequestUpdatedWindow": {
      "mode": "rolling",
      "days": 7
    }
  }
}
```

- `days` 为 1–3650 的整数。
- 每次刷新开始时冻结 `refreshStartedAt`。
- 下界为 `refreshStartedAt - days × 24 小时`，即严格的滚动时长，不按自然日截断。
- `updatedAt` 等于下界时包含；下界之后的记录包含。刷新进行期间发生的新更新也属于范围，不设置会造成误移除的“刷新开始时间”上界。

### 4.2 固定日期范围

页面接受本机当地时区下的两个 8 位日期，并把结束日期按“当天也包含”解释。持久化配置保存明确的 UTC 半开区间和保存时使用的 IANA 时区：

```json
{
  "githubRead": {
    "enabled": true,
    "pullRequestUpdatedWindow": {
      "mode": "fixed",
      "fromInclusive": "2026-07-31T16:00:00.000Z",
      "untilExclusive": "2026-08-12T16:00:00.000Z",
      "timeZone": "Asia/Shanghai"
    }
  }
}
```

上例对应页面输入 `20260801–20260812`。执行条件为：

```text
fromInclusive <= updatedAt < untilExclusive
```

- `fromInclusive` 和 `untilExclusive` 必须是规范 UTC ISO 时间，且前者严格早于后者。
- `timeZone` 必须是运行时支持的 IANA 时区。
- 页面使用保存的时区还原日期；服务器使用同一可信转换函数校验 UTC 边界确实对应所选当地日期的午夜，包含夏令时边界测试。
- 配置中不保存含糊的本地时间，也不在刷新时根据当前机器时区重新解释已保存范围。

### 4.3 兼容性与表单行为

- 旧版本化配置若没有 `pullRequestUpdatedWindow`，规范化后仍然没有该字段，配置摘要不得变化。
- 编辑旧配置的其他字段不能暗中插入 7 天窗口。
- 页面清楚显示旧配置当前为“不限时间（兼容模式）”；只有负责人主动选择并确认滚动或固定窗口后才生效。
- 新建配置草稿推荐 `rolling / 7`，但推荐值本身不等于已应用配置。
- `githubRead.enabled=false` 时保留窗口值但不执行 GitHub 读取，便于以后恢复。
- 配置合并需要深合并 `githubRead`，局部覆盖 `enabled` 时不得丢失窗口，反之亦然。

## 5. 配置影响与确认

窗口变化由受信任配置比较器根据“可被自动发现的 `updatedAt` 集合”分类：

- 从不限时间改为有限窗口、增加滚动下界、收窄固定区间：`security_tightening`。
- 从有限窗口改为不限时间、减小滚动下界限制、扩大固定区间：`authority_expansion`。
- 平移固定区间或在无法证明集合包含关系的模式之间切换：可以同时包含 tightening 与 expansion。
- 仅改变 `timeZone` 但 UTC 边界不变，不改变授权集合；若边界也变化则按边界分类。
- 当前服务在启动时注入 GitHub 读取配置，因此任何窗口变化标记为 `restart_required`，沿用已有受控配置应用与重启流程。

扩大范围可能让更多 PR 进入自动工作授权，所以仍需配置变更确认；收窄范围会撤销授权，也必须形成可审计配置版本。

## 6. 刷新与过滤流程

一次 PR 刷新按以下顺序执行：

1. 刷新服务记录唯一的 `refreshStartedAt`，把版本化配置解析为不可变有效窗口。
2. 同一个有效窗口传给 assigned 和 authored 两个搜索。
3. 适配器为 GitHub 搜索生成保守的 `updated:` 查询约束。远端约束只能缩小传输量，不能代替本地判定，也不能排除本地本应包含的边界记录。
4. 两组搜索结果都先做严格结构校验，包括身份字段和可解析、规范的 `updatedAt`。
5. 对每组结果执行精确本地窗口判断，再合并重复 PR 和关系来源。
6. 只有范围内的记录才能进入并发详情抓取和责任分类。
7. 结束前再次核验 GitHub 当前账号；账号变化使整个 PR 源失败。

任何一组查询、结构校验、窗口判定或最终账号复核失败，都使本轮 GitHub PR 源整体失败，不能提交部分结果。

## 7. 搜索上限与完整性

GitHub CLI 搜索当前每组最多请求 1000 条。配置有限窗口后，恰好达到硬上限不能被当成完整结果。

- 适配器按 `updatedAt` 时间段拆分查询，并对重叠边界按稳定 PR 身份去重。
- 分段约束必须是本地窗口的保守超集，最后仍执行第 6 节的精确过滤。
- 若某个最小可分时间段仍达到上限、返回结构无法证明分页完整、分段间出现矛盾身份，或取消信号触发，则整个 PR 源标记失败。
- 失败时沿用上一份 PR 快照并标记 stale；不得用截断结果推导范围移除。
- 未声明窗口的旧配置保留现有搜索行为和内容地址语义；本功能不借兼容升级重写其历史配置。

## 8. 快照、陈旧状态与 `left_scope`

刷新服务已有“源失败时使用上一份同类条目”的回退。时间窗口必须接入这条语义：

- 健康刷新：本轮完整 PR 集合写入快照，和上一份健康快照比较。
- stale 刷新：保留上一份 PR 项，`sourceStatus.githubPullRequests` 标记失败/陈旧；工作流快照不得产生任何 PR `left_scope`。
- 一个 PR 在健康快照中首次消失时产生一个 `pull_request.left_scope`。
- 后续健康快照仍然没有该 PR 时不重复产生事件。
- 固定范围边界按 UTC 半开区间测试；滚动范围下界相等时仍在范围内，越过下界后的下一次健康刷新才离开。

`left_scope` 是源授权生命周期事实，不只是可选业务消息。即使用户删除、禁用或误配了普通 `pull_request.left_scope` 路由，可信生命周期处理仍必须执行。

## 9. 工作授权撤销与重新进入

工作台账为自动发现来源记录持久化的范围状态，并把范围变化折入现有执行授权绑定：

- 健康 `left_scope` 把该 PR 的自动发现来源标记为 inactive，建立权限栅栏，并推进授权纪元。
- 尚未执行的岗位任务、租约、交接、交付、动作提案和确认必须失去当前权威；执行器的即时核验必须拒绝旧纪元。
- 已经完成的历史和审计记录保留，不能删除或改写。
- 同一 `headRefOid` 以后重新进入自动范围时，来源变回 active，并再次推进授权纪元。它可以产生新任务和新提案，但旧确认永远不能恢复为可执行。
- `sourceScopeId` 继续表示来源/账号范围，不包含窗口摘要；窗口版本、active 状态和授权纪元分别记录。
- 生命周期处理是幂等的：同一源事件重复投递不能重复推进纪元。

负责人显式指定一个范围外 PR 时，系统使用独立的 owner-requested 授权来源。`left_scope` 只撤销自动发现来源：

- 若没有其他有效来源，相关执行授权全部失效。
- 若存在有效的负责人显式来源，系统可以继续处理当前 Head，但必须基于该来源建立新的任务/提案/确认绑定，不能沿用已撤销自动来源的确认。
- 显式来源仍受账号、仓库、Head、Git target、能力白名单和逐项确认约束。

## 10. UI

“基础与 PR 范围”表单增加“自动发现 PR 更新时间”结构化字段：

- 最近 N 天：整数输入，旁边显示按 24 小时滚动的说明；推荐值 7。
- 固定日期：两个 `YYYYMMDD` 输入，明确提示首尾日期都包含，并显示解析后的当地时区和 UTC 边界预览。
- 兼容旧配置时显示“不限时间”，不因打开页面或保存无关字段而自动改值。
- 非法日期、开始晚于结束、无效时区、跨度越界或不能无歧义转换时，表单本地报错，服务器契约再次拒绝。
- 影响预览明确显示“收窄自动发现范围”“扩大自动发现范围”或“同时移除和新增范围”，并继续通过统一配置确认队列应用。

运行状态页显示当前有效模式、冻结后的滚动下界或固定 UTC 边界、最近一次 PR 源是否完整/陈旧；不得显示任何凭据。

## 11. 测试策略

### 11.1 配置与表单

- 旧配置省略字段后规范化形状、摘要和恢复不变。
- rolling/fixed 的合法与非法组合、未知字段、整数边界、UTC 规范化、IANA 时区和夏令时转换。
- `githubRead` 深合并不丢字段。
- 收窄、扩大、平移和跨模式切换的影响分类。
- 表单往返、兼容不限时间显示、7 天推荐不暗中应用、固定日期预览与服务端二次校验。

### 11.2 GitHub 适配器

- assigned/authored 共用同一冻结窗口和保守查询约束。
- rolling 下界相等、刚早于下界；fixed 起点相等、终点前 1 毫秒、终点相等。
- 范围外记录绝不调用详情抓取。
- 重复 PR 合并后保留关系来源。
- 缺失/非法 `updatedAt`、单侧查询失败、账号变化均使整个源失败。
- 达到 1000 条时分段、边界去重；无法证明完整时失败关闭。

### 11.3 刷新、工作流与台账

- 健康收窄只产生一次 `left_scope`。
- 源 stale 时保留上一快照且不产生 `left_scope`。
- 普通业务路由删除/禁用时，保留的可信生命周期通道仍撤销授权。
- 离开范围后任务、租约、提案和确认均不能通过即时权威校验。
- 同 Head 重新进入后授权纪元变化，可产生新确认，旧确认不能复活。
- 自动来源被撤销但独立 owner-requested 来源有效时，只允许基于新来源继续。

### 11.4 验收

- 用虚构 PR 数据覆盖所有边界和失败路径。
- 在最终稳定 HEAD 上只执行一次完整 U12；若发现真实缺陷，修复后才重跑受影响验证和最终全量门禁。
- 真实 PR 验收只允许 MyDashboard 自身读取；所有 GitHub 写动作继续停在页面逐项确认之前。

## 12. 完成标准

1. 负责人能在页面配置并确认最近 7 天或固定日期范围。
2. 配置生效后，范围外 PR 不抓详情、不进入自动岗位任务，也不反复弹出。
3. 健康范围变化可靠撤销自动授权；读取失败不会误撤销。
4. 同 Head 重新进入后旧提案/确认不可执行。
5. 旧配置、旧摘要和不限时间行为兼容。
6. 所有新增测试通过，最终稳定 HEAD 的 U12 通过，且没有发生任何未逐项确认的 GitHub 写操作。

# 测试岗位、测试库与修复循环

## 当前可用范围

测试工程师和 `verify` 代码任务会加载项目内的
[`controlled-testing`](../src/skills/controlled-testing/SKILL.md) 工作流技能。
它约定先检查相关单元测试，再按已配置的能力执行应用场景，记录证据并区分
测试未通过、环境故障、待实机验证和无法判断。技能本身不提供编译器或桌面执行工具。

现有执行器支持 Docker 中的 `node-test` 和 `node-script`。
“自动化测试库”保存脚本名称、说明、版本、正文、运行镜像、超时及工作区绑定；
每个任务复用绑定的脚本，并生成独立的执行记录。更新代码后须重新测试。

当前私有运行配置绑定的 OCT、Picasso 脚本都是仓库预检。
它们检查源码、测试资产和冲突标记；不能据此宣称已编译、运行单元测试或完成产品验收。
其他部署应以实际激活的配置为准。

## CLI 如何读取完整代码

原生 Codex App Server 开发和测试岗位现在可以在一轮模型任务中连续调用
`perform_action`、`read_source` 和 `get_state`。实际修改和固定测试由现有受控执行器
执行，每次都重新核对授权、任务状态与工作区版本。显式 `exec` 路线保留静态只读产物入口。

`read_source` 可以直接发起一次受控读取，再返回完整审计内容的分页。
`get_state.sources` 列出当前版本的已审计文件及读取进度，恢复后也能找到初始预览遗漏的文件。
内联 `read_text` 内容是预览；较长文件应继续调用 `read_source`，跟随
`nextOffset` 直到为空，并在后续页带回首个响应的 `sourceVersion`。
单页有传输字节预算，完整文件可以连续分页读取；修改后旧版本分页凭据立即失效。
该入口不开放其他作业、旧工作区版本或任意本地目录。

修改已有文件时，系统检查真实分页覆盖与原始文件哈希，不接受模型自行声明
“已读完”。缺页、取消、无效输出和清理失败不会取得覆盖凭据。新增文件继续
遵循原创建约束。旧非原生 Provider 保留原来的内联读取路径。

完整读取不扩大代码修改或测试执行权限，也不增加 Windows 编译和桌面测试能力。
写入动作仍有内容预算；重启后已预备的大文件覆盖若丢失读取凭据，会安全暂停。

连续执行的结束条件仍是必需测试通过、当前文件读取完整、最终受控 `complete` 成功。
它不会自动增加编译器、桌面或硬件测试能力。集成测试使用临时仓库与模拟测试进程；
另已用真实 Codex 和 Docker 验证小型开发、测试和变更应用链路。
这些结果与真实 OCT PR 验收分开记录，见[本次验证](validation/2026-10-14-continuous-codex-development.md)。

## 异步流程的开发验收要求

修改调度、授权、暂停、取消或 PR 版本切换时，必须测试完整生命周期。
验收要证明任务能够到达业务终态，或留下明确、可恢复的阻塞原因；
服务健康、成功入队、安全拦截以及测试总数不能单独作为流程完成证据。

PR 自动修复至少覆盖以下场景，使用真实台账、确认队列和代码任务存储：

| 场景 | 必须验证的结果 |
|---|---|
| 任务因模型输出异常暂停，随后 PR 更新 | 旧任务安全结算，新 Head 激活并能够领取 |
| 旧任务已经失败或取消 | 保留原终态和收据，新版本继续推进 |
| 旧任务仍在执行、取消中或动作结果不确定 | 等待原生停止和动作对账；确认结算前新版本不能执行 |
| 服务在上述状态重启 | 从持久记录继续结算，不恢复执行旧版本，不重复创建任务 |
| 重复巡查、重复对账、过期修订号 | 操作幂等；过期命令不能取消任务或激活新版本 |
| 授权、收据、任务或 Head 不匹配 | 保留拦截，不能借另一任务的结束记录放行 |

确认队列的 `completed` 只证明创建任务的动作完成，不能代替代码任务的终态。
有原生执行会话的任务必须经过受控停止、工作区清理和结算证明。
缺少证明的任务继续阻塞，不通过删除历史或修改状态文件恢复。

这些回归包含在常规 `npm test` 中，主要位于
`test/work-ledger-service.test.js`、`test/code-job-cancellation-integration.test.js`
和 `test/composition-root.test.js`。新增流程需同时提供成功接续和拒绝提前放行的断言，
并记录修复前失败、修复后通过的证据。

## 一次测试保存什么

- 任务、关联 PR、输入代码版本和测试时的工作区版本。
- 测试配置摘要、执行动作、开始与结束状态。
- 退出码、超时、错误信息及可用的测试统计。
- 持久化执行日志和审计产物引用。

测试库中的资产与单次执行结果分开存储。修改资产正文或说明须增加资产版本；
通过结果不能沿用到新代码版本。界面测试截图、视频及样本引用的自动归档，
需要对应执行适配器接入后才能作为实际证据使用。

## 验证失败怎么处理

`verify` 任务在固定测试失败并保存执行记录后结束本轮验证，不反复调用模型
运行同一个失败检查。恢复时会先处理已经保存的失败记录。
修改任务仍可以在其授权范围内修复后重新运行检查。

失败原因分开记录：

- **验证未通过**：检查没有通过，需要结合具体日志定位；不自动认定为产品代码缺陷。
- **验证超时**：检查未在期限内完成。
- **验证环境不可用**：测试执行器或依赖无法启动。
- **验证结果无法判断**：现有记录不足以确定原因。

失败的验证任务不能生成“已完成”的权威测试报告。测试统计中的失败数也不等于
产品缺陷数，例如缺少依赖同样可能导致测试失败。

归档和重启后保留上述失败分类。新归档使用 v3，当前版本仍读取 v1/v2；
回退应用版本前，须确认目标版本支持 v3，不能通过删除任务记录来回退。

## 本机 OCT 测试接入约定

当前没有连接远程 Windows 测试机，按本机执行设计。以下约定需要 Windows
执行适配器接通后生效，目前没有后台 UI 测试队列：

- 同一桌面串行运行测试；检测到已有 VanGogh 实例时等待，不接管或结束用户的实例。
- 只管理系统为本次测试启动且记录了 PID、启动时间、EXE 摘要和窗口身份的实例。
- 在独立构建副本中编译，保留测试输入源码版本；不让生成文件改变受控源码工作区。
- 测试脚本属于经配置激活的固定资产，任务模型只能请求执行已绑定的测试。
- 真实验收需绑定 PR、构建、测试库、数据根和样本；预检记录不能代替这些证据。
- Windows 进程监督不是操作系统沙箱；执行身份和产物使用真实的 Windows 证明，
  不伪装成 Docker 镜像。

## 要完成自动修复循环，还需接通

1. **岗位执行可用**：CLI 状态为 `available`，一次实际测试岗位任务完成。
2. **真实测试入口**：配置相关单元测试；OCT 另需 Windows 编译及 UI 执行适配器、
   对应构建、测试数据库和样本。现有 Docker Node 执行器不具备这些能力。
3. **测试驱动的修复授权**：基于真实失败证据创建独立开发任务，交付契约为
   `change-package`；不能把原本交付 `test-report` 的测试任务直接改派给开发。
4. **新版本复测**：开发交付验收后创建绑定修复版本的测试任务，保留失败历史，
   去重并防止使用旧 Head 的通过结果。
5. **真实验收**：用一个需求明确、无需硬件的 PR 跑通“失败、修复、复测通过”，
   核对日志、代码版本及覆盖范围。

这些条件未满足时，页面可展示岗位与任务状态，但不能宣布测试闭环已经可用。

## 查看后台与补充要求

部署了当前运行任务功能的服务，可在页面顶部查看正在执行的模型步骤和受控代码动作，
点击查看详情、补充要求、修改调度优先级及暂停、恢复、取消。
普通 `exec` 通道使用检查点续接：补充要求在当前步骤结束后生效，旧判断不会继续派发。
Codex app-server 通道已支持向当前回合追加要求；只有详情显示 `live: true` 且绑定当前
thread/turn 时，才表示实时引导可用。兼容 `exec` 通道仍使用检查点续接，详见
[用户指南](USER_GUIDE.zh-CN.md#当前运行任务与微调)。

检查当前服务是否已加载功能，可读取 `/api/task-runs`；返回 `404` 表示该服务版本
没有这个接口，不能通过刷新页面启用。`/api/health` 中的 `runtimeSource.headOid`
记录启动时加载的提交，和磁盘上的当前 Git HEAD 分别核对。
